# 追问：重复点击支付，会不会重复扣款？怎么解决的？

> **这是本项目最高频的追问**。回答的核心不是「我加了锁」，而是能说清**四道门各自挡什么、哪一道失效了还有谁兜底**。
>
> 所有代码从项目源码**原样摘录**，标了路径和行号；说不出精确行号就讲「文件名 + 方法名」，别编数字。
> 配套：`面试追问-问题清单.md`（追问全集）、`我负责模块-代码对照.md`（完整源码）、`项目复盘-按模板回答.md`（五段模板）。

---

## 0. 先把两个动作分开（很多人一开口就混了）

| 用户动作 | 可能出的错 | 防护位置 |
|---|---|---|
| 连点「**下单**」 | 生成多笔订单、库存被扣多次 | `OrderService.createOrder`：复用 `unpaid` 订单 + `requestId` 幂等查询 + `order_no` 唯一 + 事务内条件扣库存 |
| 连点「**支付**」 | 生成多条支付流水、`paid` 被累加、出两张收据、佣金算两次 | 下面这套「四道门」 |

**本项目库存是下单时扣的，不是支付时扣的**（`OrderService.java:156`）。所以「重复支付」不会重复扣库存；它真正会造成的是**重复写流水、重复出收据、重复结算佣金**。回答前先把这句说清楚，面试官会觉得你真懂链路。

另外要主动交代边界：**这是演示支付通道，没有真实资金账户**，不涉及真实扣款；这里说的「扣款」指订单实付金额、支付流水和收据。

---

## 1. 一句话结论（先背这句）

> 「**四道门，越往里越兜底**：Controller 层的锁挡住『同时点』，Service 的状态检查挡住『已经付过』，数据库的条件更新挡住『两个请求都读到未支付』，最后靠事务保证流水、状态、佣金、收据要么全成要么全撤。**锁只解决互斥，不解决幂等**——真正保证不重复的是状态机和条件更新。」

---

## 2. 四道门（每层：代码 → 人话 → 这道门挂了会怎样）

### 门 1｜Controller 层锁：同一订单同时只放一个请求进来

`backend/src/main/java/com/ynzx/server/controller/OrderController.java:62-79`

```java
@PostMapping("/{orderNo}/pay")
public R<Map<String, Object>> pay(@PathVariable String orderNo,
                                  @RequestParam(required = false) Integer payAmount,
                                  @RequestParam(required = false) String channel) {
    var user = AuthInterceptor.requireLogin();
    Order order = orderService.getByOrderNo(orderNo);
    if (order == null || !order.getUserId().equals(user.getUserId())) {
        return R.fail(ErrorCode.ORDER_NOT_FOUND);
    }
    // 锁在事务之外：OrderService.pay 自带 @Transactional，
    // 若把锁加在事务内部，锁会在事务提交前释放，仍然可能被并发重复支付。
    try {
        return R.ok(distributedLock.executeWithLock("pay:" + orderNo,
                () -> orderService.pay(orderNo, payAmount, channel)));
    } catch (IllegalStateException e) {
        return R.fail(ErrorCode.CONFLICT, "该订单正在支付中，请稍后重试");
    }
}
```

**人话**：锁的 key 是 `pay:{订单号}`，所以**同一笔订单串行、不同订单仍能并行**。连点两下，第二次拿不到锁，直接返回 `1005`「正在支付中」，根本进不到扣款逻辑。

**为什么锁在 Controller 而不是 Service**：`OrderService.pay` 自带 `@Transactional`。事务是在方法返回时才提交的，如果锁加在事务方法内部，锁会在**提交之前**就释放——下一个请求进来读到的还是旧状态，照样能重复支付。锁必须包在事务方法**外面**。

**这道门会挂吗**：会。锁超时、Redis 降级、多实例各锁各的，都可能让第二个请求进来 → 交给门 2、门 3。

### 门 2｜Service 状态检查：已经付过的直接拒绝

`backend/src/main/java/com/ynzx/server/service/OrderService.java:196-206`

```java
@Transactional(rollbackFor = Exception.class)
public Map<String, Object> pay(String orderNo, Integer payAmount, String channel) {
    LocalDateTime now = LocalDateTime.now(clock);
    Order order = orderMapper.selectOne(new LambdaQueryWrapper<Order>()
            .eq(Order::getOrderNo, orderNo));
    if (order == null) {
        throw new BizException(ErrorCode.ORDER_NOT_FOUND);
    }
    if (!"unpaid".equals(order.getStatus()) && !"part_paid".equals(order.getStatus())) {
        throw new BizException(ErrorCode.ORDER_STATUS_CONFLICT, "订单状态为 " + order.getStatus() + "，不可支付");
    }
```

**人话**：只有 `unpaid`（未付）和 `part_paid`（付了首付）能付。订单一旦变成 `paid`，再点支付就抛 `1502 订单状态不允许该操作`。**这就是冒烟里「重复支付返回 1502」的来源——它不是 bug，是预期的正确结果。**

`ErrorCode.java:46` 里 `ORDER_STATUS_CONFLICT(1502, "订单状态不允许该操作")`；业务异常由 `GlobalExceptionHandler.java:37-41` 转成 HTTP 200 + `code=1502` + 提示语。

**这道门会挂吗**：会。两个请求**同时**读到 `unpaid`，都能通过这行检查 → 交给门 3。

### 门 3｜条件更新（最关键的一道，真正的幂等兜底）

`backend/src/main/java/com/ynzx/server/mapper/OrderMapper.java:33-35`

```java
@Update("UPDATE orders SET status = 'paid', paid = amount, paid_at = #{paidAt} "
        + "WHERE order_no = #{orderNo} AND status = 'unpaid'")
int markPaid(@Param("orderNo") String orderNo, @Param("paidAt") java.time.LocalDateTime paidAt);
```

`backend/src/main/java/com/ynzx/server/service/OrderService.java:227-238`

```java
// 状态机推进：用条件更新保证幂等
int affected;
if ("part_paid".equals(order.getStatus())) {
    affected = orderMapper.markFinalPaid(order.getOrderNo(), now);
} else if ("installment".equals(order.getPlan())) {
    affected = orderMapper.markPartPaid(order.getOrderNo(), actual, now);
} else {
    affected = orderMapper.markPaid(order.getOrderNo(), now);
}
if (affected == 0) {
    throw new BizException(ErrorCode.ORDER_STATUS_CONFLICT, "订单状态已变更，支付失败");
}
```

**人话**：把「判断状态」和「改状态」合并成**一条带 WHERE 的原子 SQL**，由数据库行锁串行化。就算两个请求都通过了门 2，也只有一个能把 `status='unpaid'` 改成 `paid`；另一个 `affected=0`，立刻抛 1502 停下，**后面的佣金和收据一行都不会执行**。

这就是「锁 ≠ 幂等」的落点：**锁是性能与体验优化（快速挡住），条件更新才是正确性保证（谁也绕不过）**。支付回调被重复通知（第三方会重试）也是同一套逻辑。

### 门 4｜事务 + 只在成功路径插一次收据

`backend/src/main/java/com/ynzx/server/service/OrderService.java:215-258`（节选）

```java
// 支付流水
Payment payment = new Payment();
payment.setOrderId(order.getId());
payment.setPayNo(generatePayNo(now));
payment.setChannel(channel == null ? "demo" : channel);
payment.setAmount(actual);
payment.setStatus("success");
...
paymentMapper.insert(payment);

// ...（门 3 的条件更新）...

// 关键修复：重新查库拿到"已支付"的最新订单再结算佣金
// 原版传的是 UPDATE 前的旧对象，paid 仍是 0，佣金算成了 0
Order paidOrder = orderMapper.selectOne(new LambdaQueryWrapper<Order>()
        .eq(Order::getOrderNo, order.getOrderNo()));
referralService.settleAfterPayment(paidOrder);

// 支付成功 -> 自动生成电子收据
Receipt receipt = new Receipt();
receipt.setReceiptNo(generateReceiptNo(now));
receipt.setOrderNo(paidOrder.getOrderNo());
...
receiptMapper.insert(receipt);
```

**人话**：`pay()` 上有 `@Transactional(rollbackFor = Exception.class)`，流水插入 → 状态推进 → 佣金结算 → 电子收据**在同一事务里**。门 3 抛异常时，这个请求自己刚插入的支付流水会**一起回滚**，不会留下「付了钱但没状态」或「有流水没收据」的半成品。

顺带一个我修过的 bug：`:240-244` 必须**重查** `paidOrder` 再算佣金。UPDATE 前的 `order` 对象里 `paid` 还是 0，直接拿去结算会把佣金算成 0。

## 3. 「只加锁不行吗」——三个失效场景（这段最加分）

| 场景 | 锁为什么不够 | 谁兜底 |
|---|---|---|
| 锁超时 / 业务没跑完 | 当前是固定 TTL 租约（10 秒）+ 等待 2 秒，**没有看门狗续期**；TTL 一到，第二个请求就能拿到锁 | 门 2 + 门 3 |
| Redis 挂了、降级本地锁 | 降级后每个实例各锁各的，**跨实例互斥丢失** | 门 2 + 门 3（数据库层，与缓存无关） |
| 锁放在事务内部 | 事务提交前锁就释放，下一请求读到旧状态 | 门 3 的条件更新仍能拦住 |

`backend/src/main/java/com/ynzx/server/config/CacheConfig.java:68-73`

```java
if (redisAvailable(redisTemplate)) {
    log.info("分布式锁实现：Redis（自动探测可用）");
    return new RedisDistributedLock(redisTemplate, props.getLock().getLeaseSeconds(), props.getLock().getWaitMillis());
}
log.warn("⚠ Redis 不可用，分布式锁自动降级为本地锁（多实例部署下无法互斥，请显式配置 app.lock.type=redis）");
return new LocalDistributedLock(props.getLock().getWaitMillis());
```

**要主动讲这个取舍**：「降级后一致性不靠缓存，靠数据库事务和状态机；代价是跨实例互斥会丢。生产我会显式配 `app.lock.type=redis`，并补锁续期。」

## 4. 顺带挡住「少付 / 多扣」：金额由服务端算

`backend/src/main/java/com/ynzx/server/service/OrderService.java:208-213`

```java
int expect = calculatePayAmount(order);
int actual = payAmount == null ? expect : payAmount;
if (actual != expect) {
    throw new BizException(ErrorCode.PAY_AMOUNT_MISMATCH,
            "应付 " + expect + " 分，实际支付 " + actual + " 分");
}
```

`OrderService.java:177-189`（分期金额，最容易被要求现场读的一段）

```java
public int calculatePayAmount(Order order) {
    int amount = order.getAmount() == null ? 0 : order.getAmount();
    int paid = order.getPaid() == null ? 0 : order.getPaid();
    if (!"installment".equals(order.getPlan())) {
        return amount;
    }
    if (paid <= 0) {
        return (int) Math.ceil(amount * INSTALLMENT_FIRST_RATIO / 100.0);
    }
    return Math.max(0, amount - paid);
}
```

**人话**：服务端自己算应付，前端传了就比对，防止改包篡改金额。`100.0` 不能写成 `100`（否则整数除法），`ceil` 保证 100001 分的首付是 **30001 而不是 30000**——少收 1 分也是资损。对应单测 `OrderServiceUnitTest.java:28-32` 的 `assertEquals(30001, ...)`。

## 6. ⚠️ 两条别吹的口径（面试官翻 DDL 一定会问）

之前几份稿子写过「`requestId` 唯一索引」「唯一收据记录」，我核对 DDL 后更正如下。**按旧稿背会被问倒。**

### 6.1 `request_id` 是普通索引，不是唯一约束

`backend/src/main/resources/db/h2/schema.sql:273`（MySQL 版 `schema.sql:243` 同样是普通 `KEY`）

```sql
CREATE INDEX IF NOT EXISTS idx_orders_request_id ON orders (request_id);
```

而 `OrderService.java:145-152` 的 `catch (DuplicateKeyException e)` 注释写的是「唯一索引拦截了并发重复提交」——**这是防御性写法，当前 DDL 下并不会真正触发**。真正 UNIQUE 的是 `order_no`（`schema.sql:253`）和 `payments.pay_no`（`:280`）。

**被问「唯一约束在哪」就这么答**：
> 「下单的幂等是三层：先按 `(userId, requestId)` 查已有订单、复用 `unpaid` 订单、再由 `order_no` 唯一约束兜底。我核对过 DDL，`request_id` 目前只是普通索引，捕获 `DuplicateKeyException` 是防御性代码，**并不是真的靠唯一约束拦并发**——这是我会补的一项：把 `idx_orders_request_id` 改成 `(user_id, request_id)` 的 UNIQUE，并补一条并发重复提交的回归断言。」

### 6.2 `receipts` 表没有唯一约束

`backend/src/main/resources/db/h2/schema.sql:456-468`

```sql
CREATE TABLE IF NOT EXISTS receipts (
  id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  receipt_no VARCHAR(32) NOT NULL,
  order_no VARCHAR(32) NOT NULL,
  ...
);
```

`receipt_no` 只有 `NOT NULL`，`order_no` 也没有 UNIQUE。所以「唯一收据」的准确说法是：**业务上只在支付成功路径插入一次，靠门 1/2/3 保证不会走到第二次**，而不是数据库约束。

**被追问「万一有人绕过状态机直接插呢」**：
> 「会重复，这是当前边界。补法是给 `receipts` 加 `UNIQUE (order_no)` 或 `UNIQUE (receipt_no)`，让数据库做最后一道兜底；再加一条『重复支付后 receipts 行数 = 1』的断言。我现在只做了业务层保证，没做约束层保证。」

## 7. 口述稿

**30 秒版**
> 「先分清连点下单和连点支付，库存是下单时扣的，支付重复会造成重复流水、重复收据和重复佣金。我做了四道门：Controller 层按订单号加锁，同一笔订单同时只放一个进来；Service 检查状态，已支付的直接返回 1502；再用带 `WHERE status='unpaid'` 的条件更新推进状态，影响 0 行就停；最后流水、状态、佣金、收据在一个事务里，要么全成要么全撤。锁只解决互斥，不解决幂等——Redis 降级或锁超时后互斥会失效，真正兜底的是数据库状态机。验证是对最终 jar 连付两次，第二次返回 1502，收据只有一张、库存只扣一次。没做并发压测，锁也没有看门狗续期，这两块是我会补的。」

## 8. 可能被继续追问的 6 条

| 追问 | 一句话答 | 指哪段代码 |
|---|---|---|
| 锁不就够了吗？ | 锁只互斥；降级/超时后第二个请求照样进来，靠状态机和条件更新 | `CacheConfig.java:68-73`、`OrderMapper.java:33-35` |
| 1502 是什么？为什么不是报错？ | 订单状态冲突，重复支付被拒是**正确结果**；冒烟一开始把它写成「必须成功」是我的断言错，只改了测试 | `OrderService.java:204-206`、`ErrorCode.java:46` |
| 为什么用条件 UPDATE，不先查再改？ | 「先查再改」是 check-then-act 竞态，两个请求都读到 unpaid 就都放行 | `OrderMapper.java:26-35` |
| 锁为什么放 Controller？ | 事务方法返回前锁就释放，提交还没完成；锁要包在事务外面 | `OrderController.java:71-78` |
| 佣金为什么会算错？ | UPDATE 前的旧对象 `paid` 仍是 0，必须重查 `paidOrder` 再结算 | `OrderService.java:240-244` |
| 压测做过吗？ | **如实说没有**，只有功能验证；补测用 JMeter 对下单/支付做并发，看超卖与重复扣款 | 见第 5 节 |
