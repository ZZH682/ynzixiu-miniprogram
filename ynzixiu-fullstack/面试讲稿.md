## 5. 难点逐字稿（固定公式：场景 → 问题 → 方案 → 取舍 → 证据）

### 5.1 支付幂等（完整示范，主打这个）
> 「**场景**是用户网络抖动连点两次支付，或者支付回调重放。**问题**是可能重复扣款、重复生成收据、佣金重复结算。
>
> **方案**做了三层：`requestId` 幂等键让重复提交直接返回已有订单；`WHERE status='unpaid'` 条件更新推进状态机，更新行数为 0 就不再往下走；收据表按订单唯一生成。另外**锁特意放在 Controller 层包住 Service 的事务方法**——如果锁在事务内部释放，事务还没提交，另一个请求就能读到旧状态。
>
> **取舍**是：锁只解决并发互斥，不能替代幂等。所以即便 Redis 降级成本地锁、跨实例互斥失效，数据库状态机仍然兜得住。
>
> **证据**是我在最终 jar 上做过真实 HTTP 冒烟：重复支付返回业务码 1502「订单状态为 paid，不可支付」，且该订单只生成 1 张收据。」

### 5.2 防超卖（简讲 30s）
> 「**场景**是多人同时抢同一门课有限名额。**问题**是库存被扣成负数。做法是下单事务内执行 `UPDATE ... SET stock=stock-1 WHERE stock>0`，影响行数为 0 就抛库存不足，把判断下推到 SQL，不在应用层先查后改。**证据**是集成测试里校验了库存与销量扣减。配套还有分期金额：首付 `ceil(amount*30%)`、尾款 `amount - paid`，用单测覆盖了 100001 分得 30001 这类边界，避免浮点误差。」

### 5.3 Redis 降级取舍（简讲 30s）
> 「**场景**是 Redis 不可用。**问题**是缓存和锁都失效。做法是抽象 `CacheService` / `DistributedLock` 两个接口，按 Redis 可用性自动切到 Caffeine 和本地 `ReentrantLock`。**取舍必须主动讲**：降级后单机内仍然正确，但跨实例互斥能力丢失，生产上靠数据库条件更新（状态机）与事务兜底，不靠缓存。这不是完美方案，是明确的权衡。」

### 5.4 三个真实踩坑（被问「遇到过什么问题」时讲，最能证明真做过）
> 「都是联调时暴露、由我定位并修掉的：
> ① 开启 `static-path-pattern: /**` 后，Boot 3.2 找不到静态资源抛的是 `NoResourceFoundException` 而不是 `NoHandlerFoundException`，被兜底异常处理器误报成 HTTP 200 + 5000 还刷 ERROR 堆栈；补了单独 `@ExceptionHandler` 归一为真 404 + 1004。
> ② `settings.v` 在 H2 是 CLOB，用 `List<Map>` 取会拿到 `JdbcClob`，`String.valueOf` 变成 `clob0: U&...`，Jackson 还序列化出畸形 JSON；改成走实体的 `String` 属性由 MyBatis 转换，H2/MySQL 行为就一致了，并补了种子数据和回归断言。
> ③ 注册限流拦截器后出现 `WebMvcConfig → Interceptor → RateLimiter → WebMvcConfig` 循环依赖，把 `RateLimiter` Bean 抽到独立 `RateLimitConfig` 解决。
> 三个都补了回归验证，不是改完就算。」

## 6. 追问应答卡

| 追问 | 回答要点（先给结论，再给依据） |
|---|---|
| 这是真实上线的项目吗？ | 如实说：个人技术复刻，无真实用户和流量。目标是实现并验证交易一致性、并发控制、缓存，不讲 QPS，只讲取舍与验证方法。 |
| 五端都做了吗？ | 交付 H5 三端（PC / 手机 / 公众号）+ 一套后台。小程序、APP 需微信审核、上架、软著等外部资质；但 `api.js` 与 46 个接口已按可复用方式抽出，替换视图层即可接入。域名备案、真实支付 / 短信 / 点播同理。 |
| 为什么同时支持 H2 和 MySQL？ | 零外部依赖即可启动演示：dev 用 H2 MySQL 兼容模式 + 种子数据，prod 切 MySQL。两边各一份 DDL 与 data.sql，做过表集合 diff 确认一致。坑：H2 `NON_KEYWORDS` 不能含 `SET/ORDER/GROUP`；自增用 `GENERATED BY DEFAULT AS IDENTITY`；MySQL 列名用反引号包 `size/type/status/role` 等保留字。 |
| 生产库为什么默认不灌数据？ | prod 的 `spring.sql.init.mode` 默认 `never`，首次部署设 `DB_INIT_MODE=always` 建表灌种子后改回 `never`。因为 schema 带 `DROP TABLE IF EXISTS`，长期开着每次重启会清空真实业务数据——刻意做成一次性开关。 |
| 支付幂等只靠锁够吗？ | 不够。锁只解决互斥；真正兜底的是状态检查 + `WHERE status='unpaid'` 条件更新 + 事务（收据只在成功路径插一次，`receipts` 无 DB 唯一约束）。锁放 Controller 层而非 Service 内，是为了让锁释放晚于事务提交。 |
| 滑动窗口为什么用 CAS 而不是 synchronized？ | 限流是全局热点路径，`AtomicReference` 持有窗口状态 + CAS 重试，避免所有请求串行竞争一把锁；按秒取模的槽位数组，推进时清零过期槽，内存固定 O(窗口秒数)。 |
| Redis 挂了会怎样？ | 缓存按可用性在 Redis / Caffeine 间切，锁从 `SET NX` 降级本地锁。降级后单机仍正确，但跨实例互斥丢失，靠 DB 条件更新（状态机）/ 事务兜底。 |
| 哪里做得不够 / 怎么改进？ | 四块：① 没做并发压测，锁 / 限流 / 防超卖只有功能验证，也没统计覆盖率；② catalog 下发题库答案，生产应移除或改为登录后按题单下发；③ 支付 / 短信 / 点播是演示通道；④ 五端只交付 H5 三端。 |
| 46 个接口怎么统计的？ | `controller/` 下 `@GetMapping` / `@PostMapping` 计数，29 GET + 17 POST，另有 8 个类级 `@RequestMapping` 前缀不计入。 |
| 前端为什么不用框架？ | 需求是零构建、单端口、可直接双击演示；原生 JS Hash 路由 + 数据同步层足够，也避免了引入构建链。代价是大型交互的组件复用不如框架，属于取舍。 |

### 7.2 测试视角 1 分钟逐字稿
> 「这个项目我除了实现，更花心思的是怎么证明它是对的。验证分五层：4 个纯单测覆盖分期金额这类计算边界；10 个 `@SpringBootTest` 随机端口集成测试，真实启动 Spring Boot 和 H2，跑通登录、留资、题库、下单支付、收据、库存、客服留言、管理端导出；再对最终打包的 jar 做 46 项真实 HTTP 断言，重点验幂等、CSV 的 UTF-8 BOM、用户端与管理端双 token 隔离、未知路径 404；前端用最小 DOM mock 把 32 个路由逐个渲染，另外模拟后端不可达，验 9 个写动作的离线兜底。
>
> 过程中真发现并修了三个缺陷：Boot 3.2 静态路径异常被误报成 200、H2 的 CLOB 序列化出畸形 JSON、限流 Bean 循环依赖。每个都补了回归断言，形成发现 → 定位 → 修复 → 回归的闭环。」

### 7.3 能当场写出来的用例设计（被要求「设计用例」时用）

**支付幂等**
| 项 | 内容 |
|---|---|
| 前置 | 已登录用户、存在一门有库存课程、订单状态 `unpaid` |
| 步骤 | 同一 `orderNo` 连续发起两次支付 |
| 预期 | 首次 `code=0` 且生成 1 张收据；第二次 `code=1502`；`paid` 金额不变；`receipts` 仍 1 行；库存只扣 1 次 |
| 扩展 | 不同 `requestId` 重复下单复用待支付订单；并发同时支付由分布式锁串行化；Redis 不可用时降级本地锁仍不重复出据 |

**权限矩阵**：用户 token 访问 `/admin/*` → 拒绝（1003）；管理端 token 访问 `/portal/*` → 不允许越权读他人学员态；未登录访问 `/portal/me` → 1002；跨用户查他人订单 / 收据 → 拒绝。

**易漏边界**：分期首付 `ceil(amount*30%)`（100001 分 → 30001）；尾款 `amount - paid`；CSV 中文在 Excel 打开需 UTF-8 BOM；多选答案 `AB` 与 `BA` 等价；未知静态路径必须是真 404 而非 200 + 5000；金额前端「元」与数据库「分」换算不丢精度；后端不可达时页面仍可演示且页脚状态正确。

### 7.4 测试岗高频追问
- **怎么测支付 / 下单？** → 按状态机列用例：`unpaid → paid / part_paid → balance`，每个状态测合法与非法流转、重复请求、并发请求、金额边界、库存与收据一致性。
- **自动化怎么做的？** → JUnit 5 + `@SpringBootTest` 随机端口真实起服务，H2 内存库每次重建保证用例隔离；HTTP 层用 Python 脚本对打包后的 jar 做断言，测的是交付物而非开发环境。
- **发现过什么 bug，怎么定位？** → 讲 5.4 三个，重点说「先看响应码与原始报文，再定位到异常处理器 / mapper / Bean 依赖，不做试探性改代码，修完补回归」。
- **没做压测怎么补？** → 用 JMeter 对下单、支付、领券做并发场景，重点观察超卖、重复扣款、限流边界；补数据库连接池与锁等待指标；当前只做了功能验证，如实说明。
- **怎么保证用例不假通过？** → 断言业务码和落库结果，不只看 HTTP 200；幂等用例查 `receipts` 行数，CSV 用例查原始字节 BOM，权限用例查拒绝码。冒烟中曾有两条断言写错（把 1502 当失败、用 `utf-8-sig` 解码吃掉 BOM），修正后复核——**断言本身也要被验证**。
